# CliCab TEST sur le même VPS
## Diagnostic et limites
Le compose séparé réserve 80/443 : conflit probable avec Caddy production. Confirmer dans les logs hPanel (port is already allocated/address already in use). Cette variante ne publie aucun port. Elle réutilise les images staging déjà validées au SHA 572993135ce2836a383efa94479be7e5075da6cb ; le SHA de cette branche de configuration ne doit pas être utilisé comme STAGING_SHA. Aucune modification production appliquée. Un seul VPS implique CPU/RAM/disque partagés et un proxy commun : pas d'isolation physique ni de garantie de disponibilité. Vérifier ressources (free -h, df -h, docker stats --no-stream) et espace pour les images avant déploiement. Ne jamais supprimer les volumes ou exécuter docker system prune.
## Phase 1 : démarrer TEST uniquement
1. Sauvegarder la configuration actuelle du projet clicab-staging. Ne pas toucher au projet de production. Vérifier que le nouveau réseau n'existe pas déjà : docker network inspect clicab-staging-proxy ; s'il existe, vérifier Internal=true et aucun service inattendu. Sinon exécuter via SSH : docker network create --internal clicab-staging-proxy.
2. Dans le projet TEST uniquement, remplacer le compose par infra/docker-compose.staging.shared.yml, conserver les secrets et STAGING_SHA=572993135ce2836a383efa94479be7e5075da6cb. Les variables IP ne sont pas utilisées dans ce compose : elles seront utilisées au proxy commun. Garder le même nom de projet et le volume staging_db. Ne pas supprimer la base. Les anciens conteneurs Caddy TEST (s'il en reste) doivent être retirés uniquement après vérification de leur label com.docker.compose.project=clicab-staging ; aucune suppression automatique de conteneurs production. Si hPanel refuse les réseaux externes, utiliser SSH et Docker Compose avec le même nom de projet, sans créer un deuxième jeu de volumes.
3. Démarrer le projet staging ; vérifier la santé API/DB/backoffice/suivi dans hPanel. A ce stade pas d'accès Internet à TEST : c'est normal.
## Phase 2 : raccordement HTTPS (NÉCESSITE accord et fenêtre d'intervention)
Le Caddy déjà en production reste seul à écouter 80 et 443. Ajouter le réseau externe au service caddy de son compose actuel, en conservant son réseau existant (si implicite, default). Ajouter à la racine du compose networks: puis staging_proxy: {external: true, name: clicab-staging-proxy} (fusionner avec les réseaux existants, ne pas les écraser). Dans le service caddy uniquement, ajouter networks: [default, staging_proxy] si le réseau était implicite ; sinon conserver tous ses réseaux existants et ajouter staging_proxy. Ne pas connecter l'API/DB production au réseau staging.
Ajouter les trois blocs du fichier infra/staging-shared-proxy.caddy au contenu caddyfile ACTUEL, en remplaçant l'IP illustrative TEST-NET par les IP publiques exactes autorisées (/32, /128). Garder toutes les routes, volumes, variables, tags des images et configs existants. Ne pas ouvrir la liste à tous. Si un CDN/proxy est utilisé, remote_ip ne représente pas l'utilisateur : ne pas déployer avant adaptation et validation. Les trois DNS TEST doivent pointer directement au VPS actuel. Ne pas modifier les DNS production.
Avant intervention, identifier les noms exacts des projets et le fichier Compose effectivement déployé, sauvegarder le compose et le Caddyfile ; vérifier que docker compose config --quiet réussit (ne pas afficher la configuration interpolée contenant les secrets). Valider le Caddyfile avec caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile dans un conteneur de validation utilisant les mêmes variables et fichiers, sans publier de port. Après validation, ne recréer que caddy (docker compose up -d --no-deps caddy dans le projet production), en conservant volumes et images. Ne pas cliquer sur mise à jour globale qui pourrait tirer une nouvelle image pilote. Cette recréation peut occasionner une interruption HTTPS brève ; planifier, vérifier immédiatement les URL de production puis les URL TEST. Si erreur, restaurer le compose/Caddyfile sauvegardé et recréer caddy uniquement. Ne pas appliquer si l'installation réelle diffère de cette architecture.
